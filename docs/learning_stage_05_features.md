## 要理解的问题

预测时点t对应下一完整小时[t,t+1)。在t时可以使用t-1及更早的已完成上车记录，以及目标小时的日历信息。不能使用目标小时的真实记录、车费、下车位置、完成时长或未来天气。本项目也不把历史再分析天气包装成实时可用信息。

## 本项目的做法

每个区域补齐全年本地时钟小时网格；先shift(1)，再求3/24/168小时滚动均值和24/168小时标准差。滞后包括1/2/24/168小时。四周同星期同小时基准依赖168/336/504/672小时滞后，因此共同评估样本需要四周预热。夏令时不存在或重复小时设为NaN；其标签、滞后与滚动窗口受影响的样本都排除，不用零替代。

## 自检练习

练习：修改时点t之后的全部记录，验证t及以前的特征完全不变；解释为什么已知目标小时星期不是泄漏。

## 动手步骤与检查点

运行 `python -m src.run_pipeline --stage features --seed 42`；读取 feature_protocol.json 和 feature_coverage.csv。检查区域小时网格、四周预热和夏令时影响后的共同有效样本。完整源月份内的无记录小时为0，歧义或不存在的本地小时为NaN。

```python
import pandas as pd
# 教学序列：预测第4小时，只有前三个完成小时可用。
s = pd.Series([2, 4, 6, 999])
print(s.shift(1).rolling(3, min_periods=3).mean().iloc[3])  # 4.0
```

练习答案：目标小时的星期、节假日可提前知道，所以不是泄漏；目标小时的订单合计和完成结果在预测时未知，所以禁止使用。先 rolling 再 shift 在简单均值下可能恰巧相等，但统一“先移位、再滚动”更便于审查窗口边界。

纽约2025-03-09的02时不存在、2025-11-02的01时重复。原始数据没有可靠UTC偏移，不能任选一次或强行转UTC。标签或任何模型/基准窗口触及歧义的样本都从共同评估集合排除。
